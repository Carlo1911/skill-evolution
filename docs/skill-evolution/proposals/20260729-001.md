# Proposal: Add Provider Idle Timeout Pattern to hermes-provider-diagnostics

## 1. What is wrong today

The `hermes-provider-diagnostics` skill has thorough coverage of HTTP-level provider errors (401, 402, 403, 404, 429, 500) and model-mismatch patterns, but **completely misses the "provider idle timeout" pattern**: when opencode-zen accepts a connection and begins processing but stalls for 600+ seconds without returning a response. This is the single most common failure mode for Carlo's cron jobs (daily-wiki-harvest at midnight, skill-evolution-analysis at 2am, money-admin-daily-backup at 2am), yet the skill offers no diagnostic path for it.

When an agent encounters `TimeoutError: idle for 1026s (limit 600s)` in a cron job, the current skill sends them through the full HTTP-401/402 diagnostic workflow (check logs, test curl, verify models), which is the wrong path — the provider *is responding* during the day; it stalls only late at night. Without this pattern documented, every agent must discover the workaround from scratch.

## 2. Evidence

Session `20260728_080025_e2bf84c6` ("Fallo por timeout del proveedor", Telegram, 281 messages, 5 user messages) documents the full diagnostic chain:

**Three cron jobs, identical failure signature, same timeframe:**
- `daily-wiki-harvest` (midnight): `TimeoutError: Cron job 'daily-wiki-harvest' idle for 1026s (limit 600s) — last activity: waiting for non-streaming API response`
- `skill-evolution-analysis` (2am, Jul 28): `TimeoutError: Cron job 'skill-evolution-analysis' idle for Ns (limit 600s)`
- `money-admin-daily-backup` (2am): same pattern

**The agent's diagnostic (from session messages):**
- Checked cron output files — all three show the job starting normally, loading skills, then stalling
- Checked provider config: all use `opencode-zen` with `deepseek-v4-flash-free` or `big-pickle`
- Tested provider responsiveness during daytime → works fine
- Concluded: "TimeoutError: idle for ~1000s (limit 600s) — waiting for non-streaming API response" is a late-night specific issue

**Corroborated by persistent memory:**
"Provider opencode-zen (opencode.ai/zen/v1) has late-night timeout issues: multiple cron jobs fail simultaneously at midnight-2am with 'idle for 1000s (limit 600s)' while the endpoint responds normally during daytime. Diagnose with curl test. Fix: switch schedule or use opencode-go provider."

This is not a one-off — the memory records it as a recurring pattern that the diagnostic skill should document.

## 3. The change

### Current state

The skill's Symptoms & Root Causes table has entries for:
- `HTTP 401: Model X is not supported` — model mismatch
- `HTTP 401: Free promotion has ended` — expired free model
- `provider authentication failed` — gateway masking model-level 401
- Gateway threads use different provider — delegation config mismatch
- All gateway responses ~58 chars — model-level 401
- `Auxiliary: marking openrouter unhealthy` — missing credits
- `Model generated invalid tool call` — billing error (402)
- `request exceeds context size` — llama.cpp ctx-size too small

**No entry exists** for `idle for Ns (limit 600s)` or provider timeout stalls.

### Proposed addition

Add to the Symptoms & Root Causes table **between** the "request exceeds context size" row and the "Diagnostic Workflow" heading:

```markdown
| `TimeoutError: Cron job 'X' idle for Ns (limit 600s)` | **Late-night opencode-zen stall**. The provider accepts the connection and begins processing but goes silent for >600s without returning a response. Only affects cron jobs scheduled between midnight–2am Peru time (UTC-5). Daytime runs complete normally. This is NOT an HTTP error — the provider returns nothing at all. Check with `curl -w "%{http_code}" -s -o /dev/null <base_url>/models` during the affected window — if it returns 200 during daytime but stalls at night, this is the pattern. **Fix options:** (a) reschedule crons outside the 12am–2am window, or (b) switch cron-provider jobs to `opencode-go` (go tier) which doesn't exhibit this stall. |
```

Also add a new subsection at the **beginning of Step 2** (before "Verify model availability"):

```markdown
### Special case: Provider idle timeout ("idle for Ns")

When the failure message says `idle for Ns (limit 600s)`, the provider is NOT returning an HTTP error — it accepted the connection, began processing, and went silent. This is distinct from all HTTP-level errors in the Symptoms table.

**Check if this is the late-night opencode-zen pattern:**
1. Note the job's scheduled time. If it runs between midnight–2am Peru time (UTC-5), this is likely.
2. Test outside that window: temporarily trigger the cron manually (`hermes cron run <job_id>`). If it works, the provider stalls only at night.
3. **Fix options:** Move the cron schedule outside the 12am–2am window, or switch the job's provider to `opencode-go` (which does not exhibit this stall).

**Check if it's a general timeout (not time-dependent):**
1. Ping the provider's base URL: `curl -w "%{http_code}" -s -o /dev/null <base_url>/models`
2. Test a minimal completion with small token count
3. If the provider responds but the cron stalls at the LLM call, the issue may be response latency for long prompts (large wiki content, many tools). Consider increasing `gateway_timeout` or `api_max_retries` in `config.yaml`.
```

## 4. What improves, and how you would know

**Behavioral change:** When an agent encounters a cron job failure with `idle for Ns (limit 600s)` and the job runs late at night, it will:
1. Recognize the opencode-zen late-night pattern immediately instead of starting a full HTTP error diagnostic
2. Try the fix options (reschedule or switch provider) without additional discovery turns

**Verification check:** After applying, create a cron job scheduled at 1am with a simple prompt (e.g., "say hi") using `opencode-zen` provider. When it fails with `idle for ... (limit 600s)`, the agent should reference the skill's new section and suggest the fix — rather than starting a model-mismatch or credential diagnostic.

## 5. Trade-offs and risks

- **Provider-specific content:** This pattern is specific to `opencode-zen`. Users on other providers won't encounter it and the extra text adds noise. Mitigation: place it in a clearly marked "Special case" subsection so readers on non-opencode providers can quickly skip it.
- **Time-zone dependent:** The explicit Peru time (UTC-5) reference makes the pattern less useful for users in different timezones. Mitigation: phrase it as "between midnight–2am in the user's late-night window" rather than hardcoding Peru time in the skill text, and note the local-time equivalent in the evidence section.
- **May become obsolete:** If opencode-zen fixes this stall in a future release, the pattern will become stale. Low risk — the section is small and easy to remove.
- **The change adds ~500 bytes to a 18.9KB skill** — well within the growth limit.
