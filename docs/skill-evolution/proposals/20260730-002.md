# Proposal: Add Cron Script Deployment Constraints to hermes-skill-evolution

## 1. What is wrong today

The `hermes-skill-evolution` skill documents how to create the cron job (lines 96-111) and lists `scripts/skill-evolution-fetch.sh` as a "cron wrapper" (line 165), but fails to mention two critical deployment constraints:

1. **Cron scripts must be real files, not symlinks.** Hermes cron security resolves symlinks and blocks execution when the target lies outside `~/.hermes/scripts/`. The skill's `skill-evolution-fetch.sh` is a wrapper script that ships inside the skill directory or the project repo, and is commonly deployed as a symlink from `~/.hermes/scripts/` — which Hermes blocks.
2. **The cron wrapper script must resolve fetch_sessions.py relative to a stable, distro-independent path.** The current shipped `skill-evolution-fetch.sh` resolves its target script via `readlink` chains from `BASH_SOURCE[0]` — complex, fragile, and only necessary because it was designed to be a symlink.

When these constraints are violated, the cron job fails silently at the script-execution stage, producing the error `Blocked: script path resolves outside the scripts directory` — the script never runs, no NDJSON is injected, and the analysis produces zero proposals. This happened to the `skill-evolution-analysis` cron job on Jul 30, 2026, blocking two consecutive runs in one night (2am provider timeout + 7am symlink block).

**The resolution was to write a minimal wrapper that delegates to the skill's copy of the script:**
```bash

exec "$SKILL_SCRIPT" "$@"
```

This works because the skill's files live inside `~/.hermes/`, so the resolution path stays within the allowed scripts directory.

**Proposed:** Change the last row's description to:

The wrapper resolves fetch_sessions.py from its own directory, so copy it to `~/.hermes/scripts/` directly, or write a stub that delegates to the skill's copy (see Scheduled Runs below). |

### 3b. Add a subsection to Scheduled Runs (after the cron creation command)

**After line 111** (the `hermes cron create` command block), add:

```markdown
### Deploying the fetch wrapper

The cron job requires `~/.hermes/scripts/skill-evolution-fetch.sh` to be a **real file**, not a symlink. Hermes cron security resolves symlinks and blocks execution when the target lies outside `~/.hermes/scripts/`.

Deploy the wrapper by copying it from the repo/skill directory:

```bash
# Copy directly (deployed file, not symlink)
cp ~/.hermes/skills/general-skills/hermes-skill-evolution/scripts/skill-evolution-fetch.sh \
   ~/.hermes/scripts/skill-evolution-fetch.sh
chmod +x ~/.hermes/scripts/skill-evolution-fetch.sh
```

Or write a minimal stub that delegates to the skill's copy (useful when you want to keep the canonical file in the skill dir):

```bash
#!/bin/bash
set -euo pipefail
SKILL_SCRIPT="$HOME/.hermes/skills/general-skills/hermes-skill-evolution/scripts/skill-evolution-fetch.sh"
exec "$SKILL_SCRIPT" "$@"
```

**Do not** create a symlink:
```bash
# ❌ This will be blocked by Hermes cron security
ln -s /path/to/project/scripts/skill-evolution-fetch.sh ~/.hermes/scripts/skill-evolution-fetch.sh
```
```

## 4. What improves, and how you would know

**Behavioral change:** When a user sets up the cron job or hits the `Blocked: script path resolves outside the scripts directory` error, the agent will:
1. Recognize the symlink constraint immediately
2. Deploy the wrapper as a real file instead of creating a symlink
3. Know the correct stable path: `~/.hermes/skills/general-skills/hermes-skill-evolution/scripts/`

**Verification check:** After applying, create the cron job from scratch following the updated skill text. The cron should run without the "Blocked: script path resolves outside the scripts directory" error. The fetched NDJSON should appear in the analysis context.

**For troubleshooting:** The next time someone hits the blocked-symlink error and loads `hermes-skill-evolution`, the new Troubleshooting entry will point them to the fix in one turn instead of requiring the full diagnostic chain.

## 5. Trade-offs and risks

- **The skill already ships a `skill-evolution-fetch.sh`** — this change only adds deployment documentation, not new code. No risk of breaking existing installations.
- **The stub path is skill-location-dependent** — `~/.hermes/skills/general-skills/hermes-skill-evolution/scripts/` is specific to how the skill is installed under the general-skills category. If Hermes changes its skill directory layout, this path breaks. Mitigation: phrase the stub path relative to `$HERMES_HOME` when that variable is available, or add a fallback instruction to find the script via `find ~/.hermes/skills -name skill-evolution-fetch.sh`.
- **The Troubleshooting entry adds one row to a compact table** — minimal bloat. This is a real failure mode (occurred Jul 30) and the fix is non-obvious (most users don't expect symlinks to be blocked by cron but allowed everywhere else).
- **Could be merged with 20260730-001** — the two proposals touch different skills (youtube-downloader and hermes-skill-evolution) and have different evidence, so separate proposals are clearer. A reader can approve one without the other.
- **The deployed-file approach has a version drift risk** — if the skill is updated (new fetch_sessions.py arguments or wrapper logic), the copied file at `~/.hermes/scripts/` may fall behind. The stub approach avoids this because it always delegates to the skill dir's version. I considered recommending only the stub approach and removing the `cp` option, but the `cp` is simpler for first-time setup. The text recommends the stub for ongoing use.
